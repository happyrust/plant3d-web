## 0. 项目背景

- 技术栈：Vue 3 + TypeScript + three.js（WebGL2）。工厂管道模型（几十万构件）由自研 DTX 批渲染层画出；**尺寸系统**（`src/dimension/`）是一个独立内核 + 画家：内核在「设计空间（米）+ 屏幕偏移（CSS px）」里布局尺寸线、尺寸界线、箭头、数值文字、标签 billboard（位号方框 / 端点坐标卡片 / 标高药丸）、焊缝标记等，画家把它们画成 three.js 几何。
- 文字用 LibreCAD 的 **LFF 笔画字体**（线段字形），不是纹理字体：所有文字都是「描边」，与尺寸线共用同一套描边渲染。
- 目标用户是审图的工程师，常见环境是 Windows 1× / 1.25× / 1.5× DPR 的显示器与 2× 的笔记本；用户反复要求「文字的显示要更清晰」。

## 1. 现有描边渲染（`scenePainter.ts`，2026-09-14 当天四步改动之后的状态）

每条描边段是一个屏幕空间四边形（顶点 = 三维锚点 + CSS 像素偏移，顶点着色器投影后再加偏移），片元着色器按**胶囊 SDF** 着色：

- 覆盖率 `coverage = clamp((w/2 + f/2 − d) / f, 0, 1)`，`d` 到线段的距离，`w` 笔画宽（CSS px），`f` = 羽化宽 = **1 个设备像素**（`uFeatherPx = 1/dpr` CSS px）。所以**实心核宽 = w − f**，视觉总宽 = w + f。
- **两遍**：实心遍只留 `coverage ≥ 0.999`、不透明；羽化遍只留边缘、混合。两遍都写近平面常量深度 `gl_FragDepth`、`LessDepth`，于是同层描边互相**只画一次**（接头、字形笔画交叠处不叠加），对模型恒通过（叠层不被模型遮挡，工程图习惯）。
- 叠层不进宿主场景，**在整帧（RenderPass → OutlinePass → FXAA → OutputPass/ACES）之后单独一遍直接画进 sRGB 画布**：颜色写 sRGB 分量、不过色调映射、羽化边在 sRGB 里混合（ADR 0064 决定一）。
- **像素提示（hinting）**（ADR 0064 决定二 + 两段补）：
  - 屏幕字形段：宽 `hintedTextStrokeWidthPx = max(2, round(w·dpr)) / dpr`（主题 1.8 px → 1× 2、2× 4、1.5× 3、1.25× 2 个设备像素）。
  - 其余所有屏幕空间描边（尺寸线 / 尺寸界线 / 引线 / 标记 1.2 px，tag 卡片边框 1 px、位号方框 1.2 px、tag 引线 0.9 px）：`hintedLineStrokeWidthPx = max(2, round(w·dpr)) / dpr`——**下限同样是 2**。
  - 位置：`pixelSnap = 1` 的段在顶点着色器里把两端投到设备像素坐标；**轴对齐的段**（两端某坐标之差 < 0.01 设备像素）把那一坐标吸到格上——偶数宽吸整数、奇数宽吸半整数（`snapStem`），斜段不动。LFF 直笔、卡片 / 方框的直边、正视 / 俯视里的尺寸线会被吸；透视里的斜线、圆角弧段、斜引线不吸。
  - **framed 三维文字**（沿尺寸线方向、在三维平面里的数字，带白色描边光晕）不提示：透视下笔画不与屏幕轴对齐。
  - 命中区、SVG 导出仍用名义宽度与名义位置（不动内核）。

## 3. 已定决策与已知代价
- d-382（ADR 0062）：胶囊解析抗锯齿、1 设备像素羽化、两遍 + 深度去重、文字 1.8 px、药丸字高 11 px。
- d-520（ADR 0064）：叠层后画 + sRGB、文字取整最少 2 设备像素 + 直笔吸格、inspection α 0.65 / 0.35。
- d-537 → d-539（ADR 0064 补 / 补二）：**所有**屏幕空间描边取整、下限 2、轴对齐段吸格；只有 framed 三维文字不动。
- **代价（已接受但心里没底）**：1× / 1.25× 上文字、尺寸线、边框、引线**全部是 2 个设备像素**，「文字比线重」的 CAD 层次在这两档只剩颜色区分；位号方框的深色边框、2× 上的文字都「重了一档」。用户的原话是「文字的显示还要做的更清晰一些」、然后逐项拍板了「最少 2 个」。

5. **framed 三维文字**：透视里沿尺寸线的数字（2 px 笔画 + 白边光晕）没有提示，1× 上最暗像素已到名义色，但笔画软。有没有对透视文字有效的清晰化手段（例如按屏幕投影后的主方向吸格、按视线角度调整笔画宽、或者在近轴视角下退化为屏幕空间字形）？
6. **1.25× / 1.5×（Windows 常见缩放）**：`round(w·dpr)`：1.2·1.25 = 1.5 → JS `Math.round` 取 2（1.6 CSS px）；文字 1.8·1.25 = 2.25 → 2（1.6 CSS px）——1.25× 上文字与线也同宽。1.5×：文字 3、线 2。这些边界怎么定更合理？要不要把主题里的宽度改成**按 DPR 分档的设备像素表**而不是 CSS px + 取整？
7. **`snapStem` 与胶囊 SDF 的相容性**：偶数宽吸整数、奇数宽吸半整数；羽化 1 设备像素、`coverage ≥ 0.999` 判核。请核一遍：2 设备像素宽吸整数坐标时，两侧相邻像素中心距边 0.5 px → coverage = 0.5，会不会留下两条 50 % 的灰边（视觉总宽 4 行）？我们量到的是「整 2 行满覆盖、边上没有灰」——请解释这与公式的关系（是不是因为 `f/2` 项让 0.5 px 处恰为 0），并指出有没有相位下会出灰边的情形。
8. **验收方法**：我们用「横截面峰值覆盖率 / 有满覆盖像素的横截面比例 / 每横截面核像素数 / 墨量」四个指标从真实截图反解覆盖率。这套指标够不够？有没有你推荐的、与人眼「清晰 / 发灰 / 过粗」更相关的量（如 MTF、边缘对比、笔画对比度 vs. 字高的阈值）？给出可直接在 Python/PIL 上实现的定义。
