# 显示查空时按规模补齐模型，容器边取边画，新旧按库文件最新会话判

ADR 0069 把「显示」定成只查询：点眼睛不生成，查空就提示人去右键。用下来有三处不够。其一，用户要的是「这个 SITE / ZONE 没生成过就先生成再加载」，
0069 的 2026-10-14 追记只对 BRAN / HANG / SUPPO / EQUI 自动生成，工作区里已经放宽到任何节点，但没有规模上的约束，发出去的还是先删后生成（`force: true`），
查空之后要等一次整库根枚举才决定生不生成（实测 24–30 秒）。其二，容器要等全部记录、全部网格到齐才画第一帧（7400 件 2.1 秒，8 万件 11.5 秒），
期间还盖着一层整屏遮罩。其三，「是不是最新」各处说法不一：模型树的库状态圆点只比模型与已入库的数据，库文件多出 10、23、8 个会话的三个库都显示「最新」，
而「模型生成」面板对同样的库说「待更新」；节点一级没有新旧可言。2026-11-10 用户就这几件事定了下面六条
（方案与取舍的全文在 `docs/plans/2026-11-10-model-load-speed-generate-and-freshness-plan.md` 第 6 节）：

**（1）显示仍然先查询，查空时补齐。** 只有「记录查询成功、收齐、确实一条都没有」才对这个节点做模型资产补齐，补齐发的是不带 `force` 的
`POST /model/generate { refno }`——后端只生成缺的和落后的根，已有的原样返回。记录查询失败、没收齐（409、出错、预算外）、退到子树查询、或者 `/dbnums` 说这个库的模型
正在追平已入库的数据（`model_lagging`）、库正在被写（`initialization_publishing`）时，一律不补齐，只给提示。`force: true` 只留给右键「重新生成模型」和「模型生成」面板。
库里有没有模型看已经缓存着的 `/dbnums` 那一行，显示路径和状态圆点都不再调 `dbnums/{库}/model/roots`。

**（2）补齐按规模分流。** 生成单元不超过 20 个的直接生成并显示；超过的先确认一次，写明有多少个单元没有模型，可以选「只显示已有的」；
确认后按 ZONE 分块生成，做完一块显示一块，带进度。阈值由后端的生成预检给出，预检接口没上之前前端按同一个数过渡。

**（3）容器边取边画。** 按成员拆开查的节点（顶层 SITE 按它的 ZONE），每收完一个成员就把这一批装进场景，不等整个节点收齐：第一批立刻装，
之后攒够不少于已装的数量、或离上一批够久再装。相机在第一批到的时候飞一次，收齐后再对整体对一次焦，除非用户在这期间自己动过视口。
读记录期间不盖整屏遮罩，进度走查看器左下角的状态条；整屏遮罩只留给生成阶段。全部收齐才记为已加载。

**（4）「最新」按库文件最新会话算。** 库一级比三枚水位（库文件最新会话、数据入库到哪、模型按哪个会话生成）：三者对齐才是最新；
模型与数据一致但库文件还有新会话的，写「库有 N 个新会话未更新」，措辞保持中性——E3D 每次登录都会多一个会话，多数新会话没有改到几何。
SITE / ZONE 一级只在「模型生成之后的会话真改到了它下面的构件」（网格变、位置变、新增、删除）时才标落后，登录产生的空会话不算。
模型树的圆点和「模型生成」面板的徽标用同一个判定函数。

**（5）落后时先显示已有的。** 行上标出落后和原因，提供「更新到最新」；更新完成后出更新提示，人点「重载」才换场景（沿用 2026-10-26 的决定，不自动换）。
能看模型的人都可以点「更新到最新」；整库重排、清理这类重操作仍只放在「模型生成」面板里。

**（6）不为生成标记建新表。** 节点的状态由库水位、会话链、后端进程内的生成记录按需算出来（与 gen-model ADR-079「模型水位是唯一的持久模型事实」一致）；
页面里只记「装的时候是哪一版」。未初始化的库按需生成的结果只在后端内存里，后端重启就要重新生成，这一点不变。

性能目标（本机、冷态、三次取中位数）：大 ZONE 0.7 秒出图；整 SITE 0.7 秒出图、1.5 秒画完；8 万件 1 秒出图、6 秒画完；没生成过的小 ZONE 1.5 秒以内。

## Considered Options

- **查空时全自动生成，不分规模**（当时工作区里的做法）：小节点一点就出，但大节点一点就占用后端几分钟，没有进度，不能取消，误点了也在算。
- **查空时一律先确认**：几十件的 ZONE 也要点确认，烦。
- **落后就自动更新，更新完再显示**：看到的一定是最新，但把「看」变成了「改」，每次显示都可能等一个批次，任何人打开页面都会让后端开工；
  对库水位落后的库，后端会把节点下每个根整根重算。
- **更新完成后自动重载**：少点一次，但场景会自己变，要判断用户是不是正在测量或批注，判断错了会打断人。留作以后可选的第二步。
- **「最新」取数据水位**（原来圆点的口径）：界面简单，但库文件比入库的新时仍说最新，不在自动更新范围里的库永远是「最新」。
- **模型水位等于库文件最新才算最新，不看节点**：实现最简单，但 E3D 每登录一次，所有库的所有节点都变「落后」，等于没有信息（gen-model #65 的教训）。
- **后端新建一张 SITE / ZONE 标记表**：重启后还知道哪些节点生成过，但与 gen-model ADR-079 相反，每次生成多写一笔，回退、清库多一张表要管，
  和水位变成两套可能打架的事实。
- **容器维持全部到齐再画**：画面一次成型不会跳，但大节点要对着空白等十几秒。
- **边取边画按固定间隔（0.5 秒）装一批**：大场景装一批要几百毫秒，固定间隔会让装载占满主线程、拖慢取数；改成翻倍，按时间触发的间隔不短于上一批耗时的 6 倍。
- **边取边画按记录页交批次**：一个构件的记录可能跨页（BRAN 的直段记录都挂在 BRAN 自己的 refno 上），按页进缓存会互相覆盖。只按成员交，单个很大的 ZONE 不边取边画。

## Consequences

- 2026-11-10 落地的是 A1（查空不等整库根枚举）、B1（补齐不带 `force`、读失败不补齐）、A2（装载路径两处白耗）、C1（库一级新旧）、A3（边取边画）。
  2026-11-11 凌晨落地的是（2）的预检、确认框、分块生成与进度（B3）；（4）里 SITE / ZONE 一级的新旧和页面内的已加载节点表（C2）；
  （5）的「更新到最新」（C3）；网格打包取的前端一半（A4，后端没有那条路由时自动退回逐个取）。那时后端的节点模型状态与生成预检接口还没部署，
  预检（沿树往下数两层，写「约 N 个单元」）和节点新旧（`/dbnums` 那一行加一次 `node/versions?since_sesno=`）用的是过渡办法。
- 2026-11-11 上午新后端部署（`GET node/model-status`，gen-model ADR-099；`POST meshes/batch`）之后落地的是下面这些；过渡办法留着，只在服务端没有那条路由（旧构建）时走：
  - **（2）（4）接上后端的节点模型状态。** 行上的新旧（`nodeModelStatus.resolveNodeModelStatus`）和生成预检（`generationFill.planModelGeneration`）问的是同一个接口
    （`nodeModelFacts.ts`）。节点多了三种说法：「未生成」「部分生成」「没有生成单元」，未初始化的库也说得出；预检的单元数是精确的（不写「约」），
    要不要确认、阈值多少用后端回的。点过但没有模型可显示的节点也登记一行（不算已加载），行上给「生成」。
  - **补不补听后端的。** 原来节点已有一部分模型时只对「模型按需生成的库」补没有记录的 ZONE，库里有成套模型时一律不补（分不清是没生成还是本来没有几何）。
    现在接口说这个范围有单元没生成就补，说没有就不补，不看库是不是已初始化；缺的单元在「有记录、但只生成了一部分」的成员里时，最后对节点自己补一块。
    「没有生成单元」的节点、单元都生成过只是没有可画几何的节点，点眼睛不发生成，照实说。
  - **缺的单元有时归「更新到最新」，不按需生成。** 库有模型水位、在后端的更新范围里、库文件比水位新时，没有模型的单元多半是水位之后才建的：
    行上给的是「更新」，显示时已有的照常显示、缺的不生成。按需生成只进后端内存，而且水位落后时后端会把范围里的根整根重算（gen-model 规范 §4.5.3
    「不要拿 generate 去刷新到最新」）。未初始化的库、水位已经追平的库、不在更新范围里的库照旧给「生成」。
  - **落后的节点**只有库在后端的更新范围里、模型靠库水位担保时才给库一级的「更新」；不在范围里的库（更新会被拒绝）和按需生成的库（没有水位可推进）
    当时不给，提示里写明右键「重新生成模型」——2026-11-11 下午用户定了现在就加，见下面「节点一级的更新」。
    落后按净差分算（先改后改回不算），提示里写的是「生成之后有 N 个单元被改到」和起止会话，不再逐个点名会话。
    「有更新可重载」仍是页面这一层的事：库的模型水位比本页装的那一版新时，才再问一次节点版本表其间改没改到本节点。
  - **加载中可以停**（用户 2026-11-11 定）：停掉剩下的批次，把这个节点这一次画出来的收起来，回到没显示的状态；已经取到的记录和网格留在缓存里，
    再点眼睛只取没取完的。读记录、取网格、分块生成三个阶段都能停，入口是行尾的转圈和状态条上的「停」；右键重新生成不能停。分块生成中停：没发的块不发，
    在飞的那一发前端取消、后端照常算完，已经生成的留在后端。点之前就在屏幕上的构件不动。重载中停：还没开始换就停，场景保持原样。
    模型全画出来之后、顺带问后端「还有没有要补的」那一会儿不给停（这时点停会把刚装好的收回去），确有要补的、开始生成时才又能停；
    这一问最多等 3 秒，不让显示挂着；库的三枚水位对齐时不问。
  - **重载释放旧对象**：整套替换时新对象加上、重编成功之后，换下来的旧对象从图层里真的拿掉（原来只是隐藏，每重载一次对象槽多出一份）。
    重载时刚按祖先查回来的记录直接交给装载器（原来又逐个构件清掉重问一遍）；取回来的网格内容没变就不往缓冲里再追加一份。
  - **重载容器节点时撤下被删的构件**：重载要把「重载前这个节点名下的构件」和最新记录比，多出来的（数据批次删掉的）从场景撤下。原来前者只从记录缓存和
    装载器的属主链取，这两处只认得到生成根（BRAN / EQUI）为止，重载 SITE / ZONE 时差集恒为空，被删的构件留在屏幕上（2026-11-11 真机上用 E3D 删掉一台设备
    再重载 SITE 才发现）。现在显示流程自己记一份「每个节点上一次装了哪些构件」，重载时并进基线。
- 2026-11-11 下午（用户看了目标总表之后定的；方案文档第 12 节）：
  - **「缺的单元有时归更新到最新」那条规则，用户确认。**
  - **节点一级的更新**（`nodeModelUpdate.ts`；`showModelByRefno` 的 `update` 选项）。没有库一级的更新可走的库里（模型按需生成的库、不在后端更新范围里的库），
    落后的节点行上也给「更新」：只让后端把这个节点下的单元按库文件最新会话重新生成，做完直接把屏幕上的换掉（后一半就是重载）。动手之前重新问一次后端的
    节点模型状态，按它定走哪条路：
    - 没有单元被删 → 不带 `force` 的 `model/generate`（gen-model 规范 §4.5.3：「未初始化的库才对节点发不带 force 的 generate」）。后端逐根核对回执，
      不是最新会话的重新生成、已是最新的跳过，**不清任何东西**。SITE 一个 ZONE 一块，有进度，可以停。
    - 有单元被删 → 带 `force`，先清后生成（同右键「重新生成模型」），这一段不能停。不带 `force` 的生成只枚举还在的根，被删单元留在后端投影里的旧回执
      没人清，`model/records` 按祖先查还会把它们查回来（读后端代码得出，没有真机例子）。
    - **gen-model #142**：先清后生成在没修好的后端上会把别的构件、别的库共用的模型数据一起删掉。所以后端的 `/health` 没有声明
      `capabilities.mesh_purge_keeps_shared = true` 时，这条路先弹确认，用给人看的话说清楚后果；声明了就不弹。不带 `force` 的那条路不踩它，不为它问人。
    - 单元数超过后端给的阈值时先说明要占用后端一段时间。后端此刻说已经最新就不生成、直接重载；库正在更新、判不了、已经不是「全部生成过」就不动。
    - 做到一半被叫停：屏幕上的不动。已加载节点表里记一笔「本页装的不是后端现在的那一版」（后端自己看不出本页装的是哪一版）：后端说「最新」时行上给
      「重载」，说还落后时照旧给「更新」。先清后生成之后后端超时还在后台算、重载的记录没查通，也记这一笔；节点重新登记时清掉。
    - 只在单测和假接口上验过（生成请求一律不转发给正式后端）；没有在正式后端上点过——真数据里没有「落后」的例子，带 `force` 的路在 #142 修好之前也不该试。
      2026-11-11 16:10 正式后端换成了带修法的构建，`capabilities` 里已经有 `mesh_purge_keeps_shared: true`。
  - **记录按批取**（`modelRecords.collectRecordsForAncestors` 的 `batchAncestors`；方案文档第 13 节）。顶层 SITE 拆成 ZONE 查记录时，ZONE 多于 64 个的
    十几个 ZONE 打包成一发（规范 §4.5.2 现成的批量形），回执按逐根条数切回各个 ZONE——按成员的备忘、边取边画、停了再接着装看到的不变。
    头几发仍只带一两个 ZONE（第一帧不晚）；一组不超过剩下的平摊到 6 路；一批超过一页就按条数重新分组再发，不拿游标翻；批量请求没成就退回一个一发；
    后端没声明 `model_records_batch_max_roots` 时不打包。8 万件的 SITE 实测（同一份代码用页面地址上的 `gm_records_batch` 交替量，机器没有编译在跑）：
    记录请求 531 发 → 约 50 发，网格请求 251 发 → 约 35 发，全部画完 5.9 秒 → 4.5 秒；有编译在跑时只碰上一次，6.2 秒。
    **量出来比估的少省**：请求的来回只是一半，另一半是主线程自己忙不过来（这 4 秒多里长任务 2.6–3.4 秒）。所以方案里那条后端的流式新接口
    （`model/records/stream`）现在不建议做，再往下要先看主线程。
  - **三轮的改动提交到了本地 `main`**（不推送，只带这项工作的文件）。三个文件里各留了一处开工前别人的在途改动没有提交——它们依赖别人没提交的文件，
    带进去 `main` 自己过不了类型检查。
- （5）在真机上验过一遍（2026-11-11，8000 库的测试 SITE，用增量套件里成对的宏新建一台设备再删掉，各做两遍）：E3D 保存之后 15–30 秒行上变状态，
  点「重载」0.2 秒换成新模型，删掉的那台重载后从屏幕上撤下。**行上的「更新」没有用上**：这个库在后端的监听范围里，保存后十秒左右后端自己就排了批次、
  两三秒做完，行上直接到了「有更新可重载」。页面的「更新到最新」对真后端只验到「库已经最新」这一种回执；「排上了 → 在跑 → 做完」仍只有假接口上的验证。
- （2）落地时的两点取舍：
  - 确认框按场合给两个选项，不是三个并列。节点已有一部分模型时，已有的在问之前就已经显示出来了，选项是「生成并显示 / 只显示已有的」；
    一个模型都没有时是「生成并显示 / 取消」。没生成的部分记在页面里，行上给一个「生成」可以再来（已加载的节点再点眼睛只是恢复可见，不会再问）。
  - 分块生成回 504（后端 120 秒没算完）、409、503 或回执里有可重试的失败根时，隔 3、5、8 秒、之后每次 10 秒用同样的请求再问，一块最多等 10 分钟，
    不要人再点；不可重试的失败根在结束时点名，其余照常显示。生成跑过了没有可显示的东西、或有不可重试的失败的范围，本页面里不再自动重发；
    **超时的不算试过**，下次点眼睛接着问（原来是试过一次就不再发）。补齐期间进度走状态条，不弹整屏遮罩。
- （5）落地时：「更新到最新」发的是库一级的 `POST update/execute { dbnums: [库] }`，和「模型生成」面板是同一条路、同一张任务表；它更新的是整个库
  还没入库的会话，不只这个节点，点之前的确认框里写明。做完不换场景：重拉库状态，已加载节点表把真被改到的节点标成「有更新可重载」。
- `useModelGeneration.showModelByRefno`：查空分支按（1）收紧；`startProgressiveLoad` 订阅记录源的成员批次（`subscribeMemberRecords`），节奏在
  `progressiveLoadPolicy.ts`；收尾只装还没装的。`modelRecordSource` / `modelRecords` 多了成员批次的出口，显示路径仍然不出现 `generate`（源码钉 `display_never_generates` 照旧）。

  圆点多了两种画法：蓝色是「库文件还有新会话」，转圈是「库正在被写」。

- **已知的缺口**：
  - 已经发出去的单个网格请求（旧后端的逐个取）和打包取的那一批，叫停时不取消，让它回来进缓存。整库显示（`show_dbnum`）没有「停」，它的整屏遮罩也没有动。
  - 节点一级的更新没有真机验过（见上）。有单元被删时它只能先清后生成，是因为后端不带 `force` 的范围生成不撤被删单元的旧回执；后端那一侧改了之后这条路可以去掉。
  - 按需生成的库里，补齐缺的单元时如果对节点自己补了一块，后端会把这个范围里回执不是最新会话的根顺带重新生成，本页不知道（屏幕上那几根还是旧的）。
    要彻底得让 `model/records` 把每根对应的生成会话带出来。
  - 行上的状态在按需生成之后不会自己重问（生成不动库的水位）：显示流程在补齐做完、被叫停之后叫它重问；别的页面、别的人触发的生成要等下一次点它。
  - 「部分生成的节点在已初始化的库里按需补齐」在正式数据上没有例子，只有单测；「落后」这个判定在真机上也没出现过（新建单元时后端判的是部分生成，
    删掉单元时后端先一步更新完了），文字和「更新」按钮只有单测。
  - 页面刷新后「更新中」的状态不保留（后端的任务照常跑）。
  - SITE 正在边取边画时又去显示它下面的某个 ZONE，两路可能同时装同一批构件；装载器对「已装」的判断不是并发安全的。同一个节点的两路已经挡住，父子节点之间没有。
  - 边取边画会让读记录本身慢一些（8 万件大约一秒：读记录的同时主线程在装模型、连接也被网格请求占一部分），省下的是收尾，全部画完不变慢。
