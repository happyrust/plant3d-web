# 模型树与三维几何改从 gen-model `/api/v1` 取数，经数据源端口切换、旧链路保留在开关后

模型树与三维模型两条数据链的取数点不再直接调旧后端（`plant-model-gen :3100` 的 `/api/e3d/*`、parquet / DuckDB-WASM、`/files/meshes/**.glb`），而是经四个数据源端口（`TreeSource / ModelRecordSource / MeshSource / AttributeSource`，`src/model-source/ports.ts`）取数；端口后面两个适配器：`legacy` 原样委托现有函数（零逻辑，`model_source=legacy` 下逐字节同前），`gen-model-v1` 走本仓 gen-model 的 `/api/v1`（`tree/*` + `search` + `model/ensure` + `model/records` + `element/attributes` + `/api/v1/meshes/{hash}.glb`）。一个页面只有一个几何数据源：开关 `?model_source=` → `VITE_MODEL_SOURCE` → 默认 `legacy`，切到 v1 时 `useDbnoInstancesDtxLoader` 把调用方的 `parquet` / `backend` 一律改写成 v1（自带不可变清单的版本对比调用除外）。默认在浏览器两源对拍通过之前**不翻**。

**2026-09-09 追记：默认已翻到 `gen-model-v1`**（收口计划 `docs/plans/2026-09-09-gen-model-v1-closeout-and-next-steps-plan.md` D8 按 B 口径）。「浏览器两源对拍全绿」这道闸在本机拿不到：legacy 输出目录没有 `scene_tree_parquet/`（树与 `visible-insts` 空转）、parquet 只覆盖一个 ZONE 的管道（EQUI 0 几何）、dbnum 7997 没有 SUPPO，而 legacy 直管本身按元件原点到原点画、有伪影——它已不是可靠参照。改以数据级对拍（BRAN 对象数 22 = 22 且构件集相同；ZONE legacy 1287 个有几何构件全部在 v1 里；EQUI v1 40 个基本体）+ v1 浏览器 ↔ `model/records` 三类节点逐条相等 + D6 数值对拍 ≤ 0.002 mm 作为翻默认的依据（母计划 §8.13）。`legacy` 经 `?model_source=legacy` / `VITE_MODEL_SOURCE=legacy` 仍可切回，开关保留一个发布周期；legacy 路径的代码与行为不动。

**2026-09-18 追记：「一个发布周期」怎么数**（grill 第 4 轮 Q20）。仓里最后一个版本 tag 是 `v0.1.26`（2026-05-14），之后再没打过，tag 不能当锚；锚改为**生产部署**：第一次用 `deploy-ubuntu.yml` 把默认 `gen-model-v1` 的构建部署到生产 = 周期起点，其后的下一次生产部署 = legacy 开关与 legacy 链可删，硬条件是那次部署时生产环境的 `:3100` 已停。版本对比这条链的逐文件退役清单与出口在 `docs/plans/2026-09-18-model-version-compare-gen-model-v1-migration-plan.md` §7（它画的边界允许先于 legacy 整体退役单独删干净——同日用户拍板不等锚，这条链已删，见 ADR 0065 追记；开关本体与 legacy 其余链路仍按上面的锚退役）。

**2026-09-20 追记：legacy 链已删，开关随之退役**。生产切到 gen-model 当天（服务器 `:8022` 开库出树、nginx `/api` 全部指它，`:3100` 退役），按 09-18 追记定的锚一次做完：删 `src/model-source/legacy/`、`?model_source=` / `VITE_MODEL_SOURCE` 开关、`genModelE3dApi` / `genModelE3dParquetApi` / `genModelSearchApi` 与 `genModelPdmsAttrApi` 的旧后端取数函数、`useDbnoInstancesParquetLoader` / `usePtsetRuntimeLookup` / `filesOutput.buildFilesOutputUrl` 与整条 DuckDB-WASM / parquet 链（`@duckdb/duckdb-wasm` `apache-arrow` `parquet-wasm` `surrealdb` 四个依赖、`public/duckdb`）、`.glb` 网格解析分支；`ModelSourceKind` 只剩 `'gen-model-v1'`。gen-model 没有对应接口的旧后端功能连 UI 入口一并拨掉（D1）：房间树 / 房间计算、`/api/space/*` 六个支架场景（Dock 只剩 BRAN 中心线净距）、MBD v2 外部尺寸、工作台 / 任务创建 / 任务监控 / 模型导出 / 增量更新面板、日志抽屉、站点注册、Parquet SQL 调试、模型树「过滤结果分组」；能迁的迁到 v1：`/api/projects` → `health.project`、`/api/search/pdms` → `tree.search`、`/api/pdms/{ui-attr,type-info,ptset*}` → `attributes` / `keypoints` 端口、`/api/pdms/transform` → `element/ptset.world_transform` + 树节点 owner。部署侧 `deploy/nginx_remote.conf` / `deploy-ubuntu.yml` 的上游改 `:8022`，`/files/` 只剩 `review_attachments`。

服务端配套只做加字段 / 加端点（gen-model P0）：`GET /api/v1/meshes/{geo_hash}.glb` 由服务端把 rkyv 归档的 `PlantMesh` 现场编成 GLB（内容寻址，`immutable` 缓存），前端复用既有 GLB 解析；树节点与 `search` 项带 `dbnum` / `noun`；`/dbnums` 带 `ref0s`。前端因此不解 rkyv（与 rkyv 0.7 / glam 内存布局强耦合，任何一边升级都静默读歪）、不改 DTX 的按 `dbnum` 分桶（缓存、可见性、选中都靠它），`ref0 → dbnum` 改从 `/dbnums ref0s` 建。gen-model 没有单一 WORL，前端合成一个虚拟根 `gm-root:<project>:<mdb>`，children 是全部 SITE；祖先链末尾补这个根，定位算法「从根向下逐层找」不依赖顺序。「显示一个节点」= `ensure(force=false)` → 逐生成根分页 `records` → `matrix = compose(world_trans) × compose(inst.transform)`，坐标 mm / Z-up 不换算（BRAN 24381/145018 对拍 22/22 记录 ≤ 0.002 mm 后才允许这句话成立）；容器 `422 container` 按契约展开一层，`generation_pending` / `timeout` 不重试同一 refno。

否决的备选：前端手解 rkyv（脆，见上）；gen-model 生成期旁写 `.glb`（磁盘翻倍、48k 历史网格要回填、耦合发布队列的持久边界）；就地改写 `genModelE3dApi.ts` / `useDbnoInstancesDtxLoader.ts` 而不加端口层（没有回退也没法并排对拍，且大量 `*.test.ts` 依赖旧签名）；把 `dbno` 退化成「项目一个桶」（触及 `cachesByDbno` 与十几个 `resolveDtx*ByRefno(dbno, …)` 调用点，改动面远大于服务端加一格 `dbnum`）；树根做成「项目 → 每库一个节点 → SITE」两层（勾选 / 过滤 / 定位处处要特判非 refno 节点）。
