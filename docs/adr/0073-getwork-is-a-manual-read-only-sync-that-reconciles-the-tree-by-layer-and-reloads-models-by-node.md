# 「取最新」是手动的只读同步：树按层对账，模型按库发现、按节点重载，不让后端开工

后台（gen-model）发生增量更新之后，页面跟不上的地方有三处（`docs/investigation/incremental-update-frontend-sync-2026-11-12.md`）：模型树取过子节点的层从不重取，
新增、删除、改名、挪位置都看不到；整库显示（`show_dbnum`）和地址栏直装（`show_refno` / `debug_refno`）不进已加载节点表，后台换了模型页面不知道；
已有的状态栏提示和行上的「重载」只认已经在场景里的生成根，新增的构件永远装不进来。2026-11-12 用户在三种做法里选了最窄的一种，并定了边界：

**（1）只有一个手动入口。** 底部状态栏常驻一个「取最新」按钮（E3D 的 GETWORK），钉在最右端——全局提示条画在底部正中、盖在状态栏上，
放在中间会被取最新自己弹的那一句盖住。点了才同步；不自动刷新树，也不自动换模型。
现有的状态栏更新提示、行上的新旧标记照旧，提示的悬停说明里把人引到这个按钮。推送、轮询、标签页回前台这些自动触发都不接——
协调器（`modelGetWork.ts`）写成「谁都可以叫它对一次账」，以后要接自动触发不用改它，但那是另一个决定。

**（2）只读：同步到后台现在已有的状态，不让后端开工。** 取最新不调用 `update/execute`、节点一级的更新、`model/generate` 这类接口。
后台的模型落后于库文件的库和节点，屏幕上的保持原样，在给用户的那句交代里点名（「后台还没跟上」「不在后台的监听范围里：模型停在会话 X，库文件已到 Y」）；
要后端追上，用行上现成的「更新」「生成」。监听范围内的库后台正在追时，取最新有上限地等它（3 秒看一次 `/dbnums`，最多 45 秒），等到了一起换，等不到就换能换的并说明。

**（3）一轮的顺序固定，两轮不并发。** 等正在进行的装载 / 生成结束（不打断）→ `/health`（认后端重启）与 `/dbnums` → 等后台 → 刷新模型树 → 重载模型 → 派生物 → 一句交代。
运行中再点，合并成「这一轮完了再跑一轮」。

**（4）树按层对账。** 取过子节点的层全部重取一遍（请求小，不按库跳过），没取过的层不取——它们第一次展开时自然是最新的。对账是纯函数（`pdmsTreeRefresh.ts`）：
新节点的勾选态继承父节点；已有节点的展开、勾选、选中原样留着；一层没取到就保持原样、记进回执，不当成「子节点都没了」；
从根走不到的节点连同它的记录一起清掉；消失的节点再问一次库里还有没有，分清「已删除」和「挪到了树上还没展开的位置」。

**（5）模型按库发现、按节点动手，别的库的节点不碰。** 只核对「所在库的水位和装的时候不一样」的节点，问后端的节点模型状态（`node/model-status`）再定：
库里的模型比本页装的那一版新 → 重载（`showModelByRefno` 的 `refresh`，不生成）；库里已经没有它 → 撤下；后端没有它的（完整）模型、库在更新、判不了 → 不动并说明。
**不去问节点版本表（`node/versions`）「其间改没改到它」**：那条查询每来一个新会话都要把整条会话链现算一遍、节点之间不共用，真实库上一次十几到几十秒，
几个节点一起问会超时，结果是树换了、模型没换。重载只是重新查记录、和场景做差，记录才是准的——所以库的模型水位动过之后，这个库在册的节点各重载一次。
场景里的对象按构件共用：构件在两个在册节点之间挪了位置时，后重载的节点会把先重载的节点刚装上的构件撤掉，协调器给名下构件被后来者拿掉的节点补重载一次。
整库显示和地址栏直装的节点登记在取最新自己的登记表里（`modelGetWorkRegistry.ts`，带装之前的库水位和库号）；整库显示过的库在库文件前进之后查一次 SITE 名单，
后端有模型的新 SITE 装进来。节点被取最新重载过之后交给已加载节点表。

**（6）后端没有模型不等于被删了。** 后端重启之后，模型按需生成的库（未初始化）里什么模型都没有，按祖先查记录照样是「查空且收齐」。两道护栏：
协调器看到「未生成 / 部分生成」的节点不去重载；重载的记录查空且收齐时，动手撤下之前再问一次节点模型状态，
只有后端明说单元都生成过、或它名下没有生成单元、或库里没有这个节点（`REFNO_NOT_FOUND`）才撤，否则场景保持原样并说明。
第二道护栏在显示流程里，**所有的重载都过**（用户 2026-11-12 裁决）：取最新、状态栏和行上原有的「重载」、重新部署后的重装、节点更新的后一半。
服务端没有节点模型状态接口（旧构建）时只认「库里已经没有这个节点」——问模型树，树明说没有才撤。

**（7）给用户一句交代。** 树上增删改挪各几处、模型重载了几个节点、场景里多了 / 少了多少个构件（按构件去重；挪了位置、还在场景里的不算）、
撤下了几个节点（库里已经没有的，和还在库里、名下没有几何了的，分开说）、选中的构件是不是被删了、哪些库没跟到最新及原因。
同一句进提示、状态栏（常驻，悬停看逐条细节）和控制台。

## 没有做、留着的口子

- **「取最新」要不要顺带让后端更新**（对落后的库发 `update/execute`、对落后的节点发节点一级的更新）：这一期不做。做的话是在第（3）条的「等后台」之前插一步，要先定谁有权触发、对不在监听范围里的库怎么办。
- **自动触发**（推送、轮询、回前台）：不接。推送连接「连败 5 次就不再重试」的缺口这一期也没动。
- ~~**状态栏原有的「重载」、重新部署后的重装**不带第（6）条的护栏~~：2026-11-12 已补上（见第（6）条和修订记录）。还留着的一点：
  这道护栏只管「整个节点查空」。节点没有整个查空时（后端只有它一部分模型——重启之后只重新生成了其中几个单元），差出来的构件照旧直接撤；
  取最新那条路由协调器挡住（未生成 / 部分生成的节点不重载），行上的「重载」只在后端说最新或落后时才给。
- **派生物**只带上了三样：属性面板的缓存失效重取、地址栏带 `mbd_refno` 时重取 MBD 标注、房间树在这一轮有变化时整棵重取（展开会收起）。
  空间查询结果、净距 / 测量结果、批注对构件的绑定、版本对比面板没有接。

## 后果

- 取最新之后页面上的树和模型与「后台现在已有的」一致；它不保证与「库文件最新」一致——后台没跟上的部分页面也跟不上，但会说出来。
- 库的模型水位每动一次，这个库在册的节点全部重载一次，哪怕这次改动没碰到它。整库显示的页面上就是每个登记的 SITE 各重载一次：
  约 2900 个对象的 8000 库实测 2–3 秒（`docs/verification/model-getwork-2026-11-12/replay.md` 第 2.3 节）；更大的库按装进来的构件数往上走，没有量。
  要缩小范围，得有一个便宜的办法知道「这个节点之后变没变」（后端给一个按节点的轻量答复，或前端按任务的变更清单算）——留给以后。
- 重载沿用显示流程，每个重载的节点仍各出一条原有的「已从 gen-model 加载 N 个几何实例」提示，再加取最新自己的那一句。

## 修订记录

- **2026-11-12（同一天，真实增量回放之后）**：第（5）条原来是「必要时加 `node/versions`，有会话改到这个节点才重载」，后果里写着「头一次核对一个节点要等后端现算，约 10 秒」。
  在隔离沙箱里回放真实的 E3D 会话之后改成现在这样：那条查询不是「头一次」慢，而是库每前进一次都要重算，1663 个会话的库上一次 17–28 秒，
  两个节点一起问时一轮取最新 66–144 秒、超时的那次新增的构件没装进来。同一轮回放还查出并补上了「构件在两个在册节点之间挪位置会丢」的补重载、
  撤下的两种说法、按钮的位置（第（1）（5）（7）条里各加的那一句）。经过与数据见 `docs/verification/model-getwork-2026-11-12/replay.md`。
