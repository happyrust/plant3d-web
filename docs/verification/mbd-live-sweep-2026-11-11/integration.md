## 2. 变化的归因

### 2.1 做法与闭合检查

宿主六笔、求解器五笔，逐笔组合各编一遍 gen-model 要重编几十次，代价太大（两个求解器版本各只编一次）。用的是
「宿主视图 → plant-mbd CLI」这条离线的路（三个代理都校准过它与端点等价，这次又在两头和中间各对了一遍，见下）：

- 求解器六个版本各编一份 CLI（`47eb83e`、`472a224`、`94bf16b`、`3b47289`、`f49c70f`、`d31a989`，都是在快照工作树里按提交号检出编的）。
- 宿主各阶段的输入都是那个阶段的导出工具从 `.dat` 直读出来的，不是手工改的：没改过的宿主（hostpipe 的 `in-before`、host 的
  `views-all`）、只带 DTXR 那一笔（hostpipe 的 `in-after`）、host 分支（`fixtures\all`）、合并后的宿主（这次新导的 6988 个）。
- 每个对象在「各阶段的输入 × 六个求解器版本」上各算一遍数据包，沿两条路径逐步比相邻两格：**宿主在先**（联调后端 → 宿主各笔 @ `47eb83e`
  → 求解器各笔 @ 最终输入）与**求解器在先**（联调后端 → 求解器各笔 @ 联调后端的输入 → 宿主各笔 @ `d31a989`）。6988 个对象、48834 次重算，
  CLI 没有一次报错。

**输入层面先核对过**（核对过数据）：合并后的导出工具导出的 6988 个输入，与 host 分支导的 `fixtures\all` 比，6303 个逐字段相同、685 个
不同，差异恰好是 hostpipe 四笔的效果——WELD 多出 `dtxr` 1217 个（324 条 BRAN）、`head_pos` / `tail_pos` 340 条（`head_dir` 11 条、
`tail_dir` 10 条）、设备的找墙候选少 105 个（36 台）、楼板旁的墙少 11 个（5 块）与对应的视图说明，没有别的字段。管道 2425 条与
hostpipe 留下的最终输入逐字段相同；支架 2556 个视图一个都没变。也就是说**合并没有带进任何一边单独没有的输入变化**。

**闭合检查**（核对过数据，数值按 f32 相等比，只忽略 `input_refno` 与 `meta.source_version`）：

| 离线的格子 | 对的是什么 | 相同 |
|---|---|---|
| 没改过的宿主 + `47eb83e` | 联调后端 `full-3` 的答复 | 6982 / 6982（另 6 条空支管两边都没有数据包） |
| host 分支 + `47eb83e` | host 分支的离线端点答复 | 6988 / 6988 |
| 合并后的输入 + `d31a989` | 合并后的宿主的离线端点答复（`integ\final-payloads`） | 6988 / 6988（端点另加的 196 条清点不在这条路上，单独补） |

所以这条路的两头和中间一格都与真实的端点答复对得上；沿路至少被一笔动过的对象是 1607 个，正是最终答复与联调后端不同的那 1607 个，
没有「中途变过、最后又变回去」的对象。

归因里有两处不是「那一笔单独编出来的工具」给的：（1）hostpipe 的后三笔（`21bec9bdc`、`1308e46d7`、`2c50ea7a2`）共用一份最终输入，
哪一笔动了哪个对象按「输入里变的是哪个字段」分——首尾字段归 `21bec9bdc`，找墙候选 / 楼板旁的墙归 `2c50ea7a2`，`weld_number`
在 ATTA / PCOM 上一个都没多出来所以 `1308e46d7` 是 0；（2）`bf638ed3e` 在端点里补的清点（196 条）不经过求解器，按「最终的答复里有、
联调后端没有」直接记到它头上。
