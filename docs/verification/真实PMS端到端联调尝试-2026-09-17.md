## 阻塞原因与旁证

1. `GetZyModelUrl` 是 PMS 后端去调模型中心 `embed-url` 的那一跳（时序见 `pms-3d-review-integration-e2e.md` §端到端流程图：`PMS → MC: 获取嵌入地址`）。它回「接口连通失败」= PMS 服务器连不上它配置里的模型中心地址。这一跳在 PMS 服务端发生，与本机网络、代理无关。
2. 文档里历史用的线上 plant3d 地址 `123.57.182.243`（`PMS_EMBEDDED_SITE_SUBSTRING` 示例）此刻的状态：
   - `http://123.57.182.243/` → 200，`index-Cbd5Y2FX.js`，`Last-Modified: 2026-08-03`——**六周前的前端构建**，早于 09-12 起的整个校审域移植，更不含今天的修复；
   - `http://123.57.182.243/api/review/health` → **504 Gateway Timeout**（nginx 后面的校审后端没有响应）；
   - `http://123.57.182.243:3100/api/review/health` → 504；`:8022` → 连接被拒绝。
   若 PMS 配置的模型中心就是这台机，那 `GetZyModelUrl` 失败与它的 504 是同一件事。PMS 侧到底配了哪个地址，本仓看不到，要 PMS 管理员确认。

2. 「对着新后端」= 那台机上部署 gen-model `codex/model-projection-cache` **`c8d5f6b92` 及之后**（校审域 `:8022`，`review.persistence` 必须是 `rocksdb`，见 d-398 / d-410），nginx 按 `scripts/review/nginx-review-split.conf` 把 `/api/review` `/api/users` `/api/auth` `/files/review_attachments` 切到它（next-steps-plan §1.1 第 6 条：这份配置**从未部署验证过**）。

## 附带发现（与阻塞无关，但会让下次也跑不起来）

1. **`scripts/pms-api-sniffer.ts` 从未入库**：`.gitignore` 第 80 行 `scripts/*` 把它整个忽略了（`git check-ignore -v` 命中），`git log --all` 里没有它；而 `pms-chrome-devtools-flow.ts` 第一行就 `import … from './pms-api-sniffer'`。结果是新 worktree（plant-9）里 `npm run test:pms:cdp*` 直接 `ERR_MODULE_NOT_FOUND`，只有主工作树里那份 2026-05-15 的未追踪副本能用。应在 `.gitignore` 里加 `!scripts/pms-api-sniffer.ts` 并提交。
2. 脚本 `chromium.launch({ channel: 'chrome' })` 不带 `proxy` 参数，Chrome 会吃系统代理；本机 `127.0.0.1:7890` 拦 PMS 域名时只能走 `CHROME_CDP_URL` 附加自起的直连 Chrome。文档 §「附加本机 Chrome」里的 `launch-chrome-cdp.sh` 是 macOS 脚本，Windows 上要手写：
   `chrome.exe --headless=new --remote-debugging-port=9444 --user-data-dir=%TEMP%\pms-cdp --proxy-server=direct:// --proxy-bypass-list=* about:blank`。
3. `PMS_CDP_FILL_PMS_DIALOG` 轮询 28s 后弹窗里没有字段，脚本不报错、照常打印「流程结束」；真正的失败原因（`GetZyModelUrl` 不通）要自己抓响应才看得到。脚本若在 `pollTryFillPmsDialogsInContext` 超时后顺手把 PMS 域名下 `GetZy*` 的最后一个响应体打出来，下次就不用再猜。
