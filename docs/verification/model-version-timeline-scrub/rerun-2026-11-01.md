### A4 唯一失败：`frameCache.property.test.ts` Property 16

与本特性相关（文件在 `src/utils/versionScrub/`），但这是随机种子问题，不是回归：

- 同一文件在 A3 里通过，A4 里换了种子才失败（`seed: -97184843`，失败前跑了 9 例）。
- 测试与 `frameCache.ts` 自 `b76746ca`（2026-10-29）之后没改过，工作区也没有未提交改动。
- 收缩后的反例（`limit = 0`）：

  ```
  protect [9] → put key9 → protect [] → putShared key0 from key0 → trim
  ```

  第 4 步的 `putShared` 源键 key0 不在缓存里，实现按设计原样返回 `state`（测试自己也断言 `r.state === prev`、`effects` 为空）。但 `checkStep` 紧接着用 `enforced = true` 检查「超限时剩下的键必须全受保护」：此时 key9 已经失去保护，`limit = 0` 下仍留在缓存里，于是第 247 行 `expect(protect.keys.has(k)).toBe(true)` 失败。
- 初步判断：**测试的判定条件太严**，不是实现缺陷。「源键不存在时 no-op」与「每步之后都必须满足上限」在「刚取消保护、还没有触发淘汰」的状态下互相矛盾。参考模型 `modelPutShared` 在源键缺失时也是 no-op，和实现一致。
- 按要求没有修。可选修法（需要确认）：源键缺失这一支把 `enforced` 设为 `false`；或者实现在源键缺失时也按当前保护集合 trim 一次。后一种会改变行为，需要先改 design 里 Property 16 的表述。
