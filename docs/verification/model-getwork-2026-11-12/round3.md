## 2. 七项：改了什么、怎么验证的

### 2.1 原有的「重载」也带上「记录查空不等于已删除」的护栏（第 1 项，`67661a11`）

**原来**：只有取最新发起的重载带这道护栏（选项 `confirmEmpty`）。状态栏提示上的「重载」、已加载节点表行上的「重载」、节点更新的后一半、
重新部署后的重装，重载时记录查空且收齐就直接把节点从场景撤下，并弹「在最新记录里已没有几何（已删除或成员已删光），已从场景撤下」。
后端重启之后，按需生成的模型（不在后端更新范围的库里的节点，模型只在后端内存里）没了，记录同样查空且收齐——屏幕上还在库里的东西被拿走，还告诉人「已删除」。

**现在**：`confirmEmpty` 这个选项去掉了，所有的重载都过这一道（`useModelGeneration.ts` 的 `emptyRefreshMeansRemoved`）：

- 记录查空且收齐时先问 `node/model-status`。后端说 `latest` / `lagging` / `empty`（它有这个节点的模型，名下确实没有几何），
  或者回 `REFNO_NOT_FOUND`（库里已经没有这个节点）——才撤。
- 后端说 `not_generated` / `partial` / `updating` / `unknown`，或这一问没问到：不撤，场景保持原样，弹
  「[警告] … 重载未完成：记录查空，但〈原因〉——没有当成已删除，场景保持原样」，这次重载记成没做成，并重查这一行的状态（回放里行上改成了「生成」）。
- 后端没有 `node/model-status` 接口（旧构建）：退到问模型树（`tree/ancestors`），树说库文件最新会话上没有这个节点才撤；节点还在就保持原样——
  分不清是成员删光了还是后端没有它的模型时，宁可不撤。
- 确认的这一会儿被叫停：还没开始撤，场景保持原样。

文档一起改了：`CONTEXT.md` 的「有更新可重载」「重载」两条里把「最新记录里已经没有的构件（被删掉的）」「查空即撤下」改成上面的说法；
ADR 0072 第 83 行那条「重载」的行为加了 2026-11-12 的追记；ADR 0073 第（6）条从「取最新发起的重载才带」改成「所有的重载都带」。

**怎么验证的**

- 单测（`useModelGeneration.genModelV1.test.ts`「重载查空的护栏」一组）：按旧行为写的 3 条随行为改写（原来断言「查空且收齐就撤」，现在给出后端的确认才撤）；
  新增：四种「后端没有它的完整模型」的判词各自不撤、原因照实说；这一问没问到；旧后端的几种（树说没有 → 撤；树说还在、树回了别的失败、树回了失败没说原因、树也没问到 → 不撤）；
  状态栏 / 行上 / 重新部署后的重装（只带 `refresh`）；节点更新的后一半；确认期间被叫停（问节点状态时、问模型树时各一条）；取最新发起的（不弹那一句，原因照实记进控制台）。
  记录没收齐时本来就不撤、不为它白问一次（原有两条，加了取最新发起的两条）。
- 源码钉（`ViewerPanel.getwork.test.ts`）：重新部署后的重装派发的就是 `showModelByRefnos { refreshModel: true, flyTo: false }` 这个事件。

  - 改之前（`91906363`）：BOX 被撤下，弹「[提示] 24382_1911 在最新记录里已没有几何（已删除或成员已删光），已从场景撤下」。

### 2.3 状态栏「数据已更新」的提示不再漏报（第 3 项，`b177678d`）

**原来**：一个批次和本页有没有关系，靠两条认：批次的库是不是「当前激活的库」（最近一次往场景里装实例的那个库，只认一个），或者批次里的单元根在不在场景里。
页面同时装着两个库的节点时，只有最后装的那个库的批次会出提示；经上层 ZONE / SITE 装进来的单元按单元根也认不出。上一轮回放里漏了三步（S1、S6、J1）。

（`useModelGetWork.ts` 的 `loadedModelDbnums()`），再加原来认的当前激活的库（空间查询这类不进登记表的装法靠它）。

### 2.4 一次重载几个节点时的次序（第 4 项，`ef4b9b85`）——先实测，确认存在，再修

**隐患是什么**：场景里的对象按构件共用，一个构件一个对象，不分是哪个节点装的。构件从节点甲挪到节点乙之后，先重载乙（装上这个构件）、再重载甲
——甲上次装过它、这次的记录里没有，于是把它撤掉，撤的正是乙刚装上的那个对象。次序反过来（先重载失去构件的甲）没事。

**实测（改之前的代码 `91906363`，沙箱后端，16:24:07–16:29:46；`round3/results/r3-reload-before.json`）：存在。**

| 步 | 做了什么 | 结果 |
|---|---|---|
| A1 | 管道从 ZONE Z 挪到 Z2 之后，派发状态栏「重载」/ 重新部署后的重装用的那个事件，次序 [Z2, Z] | 管道的 9 个构件从屏幕上消失（后端各 1 个实例，场景里 0 个对象）；场景对象 24 → 15 |
| A2 | 管道挪回 Z，次序 [Z, Z2] | 同样缺这 9 个 |
| A3 | 设备从 Z 挪到 Z2，等两行都出「重载」，先点 Z2 那一行、再点 Z 那一行 | 缺 1 件（BOX `24384_47480`）；两行都显示「最新」；再点「取最新」也补不回来 |
| A4 | 设备挪回 Z，先点 Z2（这回是失去设备的）、再点 Z——对照 | 对上 |
| B1 | BOX 从设备 EQ-CASE 挪到 EQ-RN（两台都是单独装的）之后，**真的去点状态栏提示上的「重载」** | 提示「库 8000 已更新到会话 1696→1698（改 4 项，场景内 2 根受影响）」，重载名单 [EQ-RN, EQ-CASE]（得到的在前）；点完那个 BOX 没了 |
| B2 | 另一页派发同一个事件，次序 [EQ-RN, EQ-CASE] | 同样丢 |
| B3 | 第三页次序 [EQ-CASE, EQ-RN]——对照 | 对上 |

状态栏那份重载名单的次序是批次回执里单元的次序，这一次正好是得到的在前。A1、A2、B2、B3 等的是查看器的回执（重载确实做完了才比），不是固定等待。

**改法**

- 同一个事件里的几个根共用一份账（`ModelReloadRound`，记这一轮里已经装上的构件）：`ViewerPanel.vue` 处理带 `refreshModel` 的事件时在循环外面开一份，
  每个根的重载都带着它；重载装完把这次装上的构件记进账，后面的根撤「上次装过、这次记录里没有的构件」时跳过账里的。
  节点整个查空撤下时也一样（它带走的构件里跳过账里的）。两轮各管各的：上一轮装过的构件，下一轮照常可以被撤。真被删掉的构件照常撤。
- 行上一个一个点「重载」不是同一个事件，没有共用的账。这种情形下做到的是不让它悄悄缺着：撤掉的构件（真有对象被撤的才算）如果还登记在别的已装节点名下，
  就给那个节点记一笔「名下有构件被别的节点的重载撤下了，屏幕上可能缺构件」——它的行上重新给「重载」，取最新也会重载它。

**怎么验证的**

- 单测 16 条（「重载几个节点时的次序」一组）：同一轮里先重载得到的、再重载失去的，不撤；失去的那个整个查空也不撤别人刚装上的；真删掉的照常撤；次序反过来；两轮各管各的；
  三个节点的两条（一个节点的构件分别挪到另外两个节点：它还剩一个 / 它整个查空）；
  不在同一轮里的九条（记一笔、整个查空撤下时同样记、本来就没有对象的不记、没有登记在别的节点名下的不记、只按真撤掉对象的那几个找——这几种在「少了几个构件」和「整个查空」两条路上各有；
  一次撤掉别人名下的两个构件只记一笔；带走的构件分别登记在两个节点名下各记一笔）。
  源码钉 1 条（带 `refreshModel` 的事件在循环外面开一份账、每个根都带着）。
- 最终代码上同一份脚本（18:26:28–18:32:19，37 项全过；`round3/results/r3-reload-after.json`）：A1、A2、B1、B2 都对上（场景对象 24 → 24）；A4、B3 照旧对上。
  A3：两行点完仍缺那 1 件，但 Z2 被记了一笔、行上又给「重载」；再点「取最新」（350 毫秒）：「已取最新：模型树挪位置 1；模型重载 1 个节点。」之后对上，期间只弹这 1 条。

## 5. 给模型加载那条线

### 5.1 已加载节点表在后台问 `node/versions` 的慢查询

**现象**：库的模型水位一动，已加载节点表里这个库的每个节点各发一次
`GET /api/v1/node/versions?dbnum=…&refno=…&scope=subtree&since_sesno=…`，一次十几到三十几秒；行上的「重载」要等它回来才出。

**触发条件**（`useLoadedNodeStatus`）：库水位变了——任务流报批次跑完时立刻重拉 `/dbnums`，或表里有节点时每 60 秒重拉一次——之后对表里这个库的每个节点重问状态；
判出「库的模型水位比本页装的新」（判词 `latest` / `lagging`、不是按需生成的）就问这个节点自上次装载以来有没有被改到，同时最多 2 个节点。

**量到的耗时**（沙箱后端，8000 库 1698 个会话，`since_sesno=1695`；五遍：改之前 16:24，最终代码 17:06、17:21、17:35、18:26）

| 量什么 | 结果 |
|---|---|
| 后端闲着，单问一个 ZONE（`scope=subtree`） | 22.7 / 20.2 / 15.9 / 17.4 秒。后端自报（18:26 那遍）`elapsed_ms` 17352：`index_diff_ms` 10209、`set_build_ms` 5853；`sessions` 1698、`windows_with_changes` 1694、`candidates` 51033、`in_scope` 194、`sets_built` 1699；后端进程的处理器时间 17.3 秒 |

| 单问一台设备（`scope=self`） | 13.5 / 12.7 / 13.0 / 10.4 / 10.1 秒（`index_diff_ms` 9274–12619，`set_build_ms` 16–23，`sets_built` 19） |

这些数是沙箱（本机、副本、小工程）上的，现网的库更大、会话更多，没有在现网上量。

对取最新的影响：取最新不等这条查询（它自己问库水位和节点状态），所以 0.4–0.6 秒就做完；受影响的是人不点取最新时行上的「重载」出得慢。

### 5.2 「同一个构件在场景里有两个对象」的成因

上一轮记的那一次（`replay.md` 第 3.2 节第 4 条，当时原因没查明）这一轮又出现了两次，查清了：点子节点的眼睛之后紧接着（约 150 毫秒内）点它的父节点，
两路装载重叠，父节点那一路把子节点正在装的构件又装了一遍。ADR 0072「已知缺口」里写的就是这件事：装载器对「已装」的判断在一路装载末尾才更新，不是并发安全的。
控制台日志对得上：父节点那一路的 `load_scope_refnos` 排在子节点那一路的收尾行之前，`loaded_refnos=23 skipped=0`；不重叠时是 `loaded_refnos=22 skipped=1`。

之所以回放里会这么点，是回放脚本自己的毛病（第 6 节）：它以为等到了子节点装完，其实没有等。脚本改对之后基线不再出现（两遍）。
人手快也点得出来。下一次重载这个节点之后恢复成一个对象。属于模型加载那条线，这里只记，没有改装载器。
