# 三维校审 · 模型中心 3100 口被旧后端占用：判定与两条修复路径（给运维 / PMS 侧）

> 2026-09-29。适用对象：管 `123.57.182.243` 这台 Ubuntu 的运维（第 4 节），以及管 PowerPMS 配置的同事（第 5 节）。两条路任选其一即可让 PMS → 模型中心恢复；**推荐两条都做**：B 是长期正解，A 是立刻止血。
> 背景合同见同目录《PMS对接清单-模型中心地址与两个接口-2026-09-21.md》第 1 节与第 7 节第 28 项；线上证据见 `docs/verification/online-3d-review-acceptance-2026-09-28/README.md` §7。

## 0. 一页结论

| 项 | 内容 |
| --- | --- |
| 现象 | PMS 里「新增三维校审单 / 送审 / 同意 / 驳回」报 **「接口连通失败，异常信息：」**；只有打开单据时的 `GetZyModeInfo` 还能回 token |
| 根因 | PMS 后端配的 `ModelRootUrl = http://123.57.182.243:3100`；3100 本该由 nginx 兼听（与 80 同一套内容），但**已退役的 plant-model-gen `web_server` 又起来了并抢占了 3100**，nginx 绑不上，PMS 的请求全打到旧后端 → 旧后端不认识新校审路由（500 / 504） |
| 与前端部署的关系 | 无关。前端与 `/api` 都在 80 / 443 上正常（09-28、09-29 两次全流程验收在 80 口全通） |
| 修法 A（运维，5 分钟） | 服务器上停掉旧 `web_server`，`nginx -t && systemctl reload nginx` 让 nginx 重新听 3100 |
| 修法 B（PMS 侧，改一个配置） | 把 `ModelRootUrl` 改成 **`http://123.57.182.243`**（80，不带端口）；改完后 nginx 里的 `listen 3100` 可以撤 |
| 验收口径 | 登 PMS 后页内 `POST /HD/PreValidate` 回业务答案（`success:true` 或「当前单据已处于终态 …」之类），**不再是**「接口连通失败」 |

## 1. 现象与证据（均为公网直连实测）

2026-09-28 23:2x 与 2026-09-29 02:3x 两次对照，结果一致：

| 请求 | `:80`（nginx → gen-model） | `:3100`（现在是旧 web_server） |
| --- | --- | --- |
| `GET /version.json` | 200，`Server: nginx/1.24.0`，commit 与 origin/main 一致 | **404**，响应头**没有 `Server: nginx`**，带 tower-http 的 CORS 头 |
| `GET /` | 200 前端首页 | `307 → /console`（旧后端自己的控制台） |
| `GET /api/review/health` | 200 `{"status":"ok","database":"healthy"}` | **504** `校审数据库连接失败: WebSocket … Server sent no subprotocol` |
| `GET /api/v1/health` | 200，gen-model 0.1.30 健康体 | 200，但是带 `litefs` 字段的**旧版**健康体 |
| `POST /api/auth/token` | 200 签 token | 200 签 token（签名与 80 一致——所以 PMS 的 `GetZyModeInfo` 还活着，掩盖了问题） |
| `POST /api/review/workflow/verify`（带 token） | 200 业务答案 | **500** |
| `POST /api/review/embed-url` / `workflow/sync` | 200 | **500** |

PMS 侧（SJ 登 `pms.powerpms.net:1801`，页内只调只读接口，09-28 23:24）：
`GetZyModeInfo` → 200 `{"ip_addr":"http://123.57.182.243","token":"eyJ…"}`；
`PreValidate form_id=FORM-CB658BB5921A&action=active&role=sj` → **`{"message":"接口连通失败，异常信息：","success":false}`**（换单同样）。同一张单直连 80 口 `workflow/verify` 回「当前单据已处于终态 approved」，说明模型中心本身没问题，坏的是 PMS 到 `:3100` 这一跳。

## 2. 为什么会这样（给排障的人）

1. 仓库 `deploy/nginx_remote.conf` 的 server 块同时 `listen 80;` 和 `listen 3100;`（2026-09-21 为迁就 PMS 现配的 3100 加的，注释写明「PMS 改成 80 后可去掉」）。
2. 旧后端 plant-model-gen `web_server` 2026-09-20 退役，但它的 systemd unit（或某个手工 `nohup` 进程）后来又被拉起来，抢先绑定了 `0.0.0.0:3100`。
3. 前端每次部署都会 `nginx -t && systemctl reload nginx`。`nginx -t` **只查语法不试绑端口**，所以是绿的；`reload` 时新 worker 绑 3100 失败，nginx 记一条 `bind() to 0.0.0.0:3100 failed (98: Address already in use)` 后**静默沿用旧配置**，80 口照常服务。部署脚本只探 80，因此部署日志也是绿的。
4. 部署日志里另有两条 `[warn] conflicting server name "123.57.182.243" on 0.0.0.0:80 / :3100, ignored`：服务器上还有**另一份**同 `server_name` 的 server 块（多半是别的配置文件遗留），nginx 忽略了后加载的那份。目前 80 口仍由正确的那份在服务，但这是隐患，顺手清掉（见 4.4）。

## 3. 先判定（服务器上，root）

```bash
# 谁占着 3100？应该是 nginx；现在多半是旧 web_server
ss -ltnp | grep ':3100'

# 找它的 unit / 进程
systemctl list-units --type=service --all | grep -iE 'plant|web_server|model|gen'
ps -eo pid,user,etimes,cmd | grep -iE 'web_server|plant-model-gen' | grep -v grep

# nginx 是否真的绑上了 3100（reload 失败的痕迹）
grep -n '3100' /var/log/nginx/error.log | tail -n 20
curl -sI http://127.0.0.1:3100/version.json | head -n 3   # 正常应 200 且 Server: nginx；现在是 404 无 nginx 头

# 同名 server 块在哪两份文件里
grep -rn 'server_name 123.57.182.243' /etc/nginx/
```

从任意外网机器也能判：`curl -sI http://123.57.182.243:3100/version.json` 若 200 且有 `Server: nginx` 头 → 已恢复；404 且无 nginx 头 → 仍被旧后端占着。

## 4. 修法 A：服务器侧停旧后端，让 nginx 重听 3100（运维）

### 4.1 停旧后端
```bash
UNIT=<第 3 步查到的旧 web_server unit 名>      # 例如 plant-model-gen-web.service
systemctl disable --now "$UNIT"
systemctl mask "$UNIT"                         # 防止再被 enable / 依赖拉起；将来真要用再 unmask
# 若不是 unit 而是裸进程：kill <pid>；再看是不是 cron / rc.local / 别的 unit 拉起的，把源头去掉
ss -ltnp | grep ':3100' || echo '3100 已空'
```
> 确认无人依赖旧后端：它只剩 parquet / GLB 的 `/files/output`、`/files/meshes`，nginx 早已不反代这两条（见 `deploy/nginx_remote.conf` 注释）；gen-model 自带模型服务。若拿不准，先 `systemctl stop` 观察一天再 `disable`。

### 4.2 让 nginx 重新绑定
```bash
nginx -t && systemctl reload nginx
tail -n 5 /var/log/nginx/error.log          # 不应再出现 bind() … 3100 failed
ss -ltnp | grep ':3100'                       # 现在应是 nginx
```

### 4.3 验证
```bash
curl -sI http://127.0.0.1:3100/version.json | head -n 3          # 200 + Server: nginx
curl -s  http://127.0.0.1:3100/api/review/health                  # {"status":"ok","database":"healthy"}
# 与 80 口逐字一致：
diff <(curl -s http://127.0.0.1/version.json) <(curl -s http://127.0.0.1:3100/version.json) && echo '80/3100 同一套'
```
然后按第 6 节做 PMS 侧验收。

### 4.4 顺手：清掉同名 server 块
按第 3 步 `grep` 的结果，保留 `/etc/nginx/sites-enabled/plant3d-web`（或 `conf.d/plant3d-web.conf`，由部署脚本维护），另一份改名 / 移出 `sites-enabled` 后 `nginx -t && systemctl reload nginx`，warn 应消失。

### 4.5 回滚
旧后端：`systemctl unmask <unit> && systemctl enable --now <unit>`。nginx 配置由部署脚本每次覆盖，回滚 = 重新触发一次 `Deploy Frontend To Ubuntu`；上一份配置也留在 `/etc/nginx/sites-available/plant3d-web.bak-<时间戳>`。

## 5. 修法 B：PMS 侧把 `ModelRootUrl` 改成 80（PMS 同事）

1. PMS 后端配置项 **第 28 项 `ModelRootUrl`（洲影模型根地址）**：`http://123.57.182.243:3100` → **`http://123.57.182.243`**（不带端口；如需 https 亦可 `https://123.57.182.243`）。这是 PMS 后端调 `auth/token`、`embed-url`、`workflow/verify`、`workflow/sync` 等七条路由的基址，与第 22 项前端嵌入地址同口。
2. 配置若被 PMS 进程缓存，重启 / 重载 PMS 后端服务一次。
3. 按第 6 节验收。
4. 通了之后告知模型中心侧：我们把 `deploy/nginx_remote.conf` 里的 `listen 3100;` 去掉并重新部署一次，3100 彻底收掉（届时旧后端占不占 3100 都无所谓，第 4 节仍建议做，避免它耗资源 / 误导排障）。

**模型中心侧**：`curl -sI http://123.57.182.243:3100/version.json`（走 A 时应 200 + nginx 头）；`node scripts/online-review-acceptance.mjs smoke`（仓库根目录，探 80 口的 token / embed-url / 嵌入页）。

## 7. 长期建议

- 部署脚本 `deploy/deploy_frontend_bundle.sh` 的「Verifying nginx and public entrypoint」只探 80；在 PMS 改 80 之前，建议同时探 `127.0.0.1:3100/version.json` 并要求 `Server: nginx`，reload 绑不上就让部署红掉，不再静默。
- 旧 `web_server` 的 unit 直接 `mask`，避免第三次复活。
- PMS 改 80 后立刻去掉 `listen 3100`，让「3100 是谁」这个问题不再存在。
