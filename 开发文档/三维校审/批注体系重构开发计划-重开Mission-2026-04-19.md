# 批注体系重构开发计划（重开 Mission）

> 日期：2026-04-19  
> 适用仓库：`plant3d-web`、`plant-model-gen`  
> 目的：在原批注体系重构资料有效的前提下，重新打包一套可直接发起的新 Mission 规划，绕开本次 mission runner 无法启动的阻塞。

## 1. 背景与当前阻塞

现有批注体系重构已经完成较充分的方案沉淀，包含：

- 7 个里程碑的主任务拆分；
- `ReviewSnapshot` 统一恢复思路；
- detached comment source、`annotationKey`、`reviewRound`、task-scoped draft、dual-layer rendering 等关键设计；
- 对 `plant3d-web` 与 `plant-model-gen` 的跨仓契约联动要求。

当前阻塞不是方案缺失，而是 **已有 mission artifacts 虽然有效，但 mission runner 无法正常起跑**。为了避免继续在同一 mission 目录上消耗时间，本次采用“重开 Mission”的方式重新提交规划包，让下一次执行从全新的 planning package 启动。

## 2. 目标与非目标

### 2.1 目标

- 重新整理一份可直接交给新 Mission 使用的执行计划；
- 明确两仓边界、阶段入口条件、输出物与验证重点；
- 保证重开后仍沿用原有 7 个 milestone 主线，不丢失既有分析成果；
- 让下一次 Mission 可以先从低风险、可验证的恢复统一与评论解耦切入。

### 2.2 非目标

- 本文档不替代详细接口契约文档；
- 本文档不直接改动任一仓源码；
- 本文档不新增第 8 条实施主线，只对既有 7 个 milestone 做重开整理；
- 本文档不处理 mission runner 本身的技术修复，仅为“重新发起 mission”提供清晰输入。

## 3. 范围

### 3.1 `plant3d-web`

- reviewer / designer 侧批注、评论、确认、恢复、返回重提相关前端逻辑；
- `ReviewSnapshot` 适配、replay、restore、tool store、review store、viewer layer；
- annotation thread UI、confirmed record 区域、task-scoped drafts、双层渲染；
- 实时协同的前端收敛与兼容回退。

### 3.2 `plant-model-gen`

- review records / comments / workflow sync 等接口元数据扩展；
- `annotationKey`、`workflowNode`、`reviewRound` 等字段契约；
- comment / record / workflow history 的兼容窗口与读写语义；
- websocket 事件体的收敛与幂等刷新支撑。

### 3.3 跨仓统一要求

- 平台内 restore、workflow/sync restore、import restore 语义一致；
- 评论真源与批注实体关系稳定；
- 同一 `taskId` 在返回/重提/重开中保持连续性；
- 所有迁移阶段具备 feature flag 或兼容回退路径。

## 4. 重开后的 7 个里程碑

## M1：术语、契约与迁移边界冻结

**入口条件**
- 已确认原始计划、补遗、mission artifacts 可作为参考；
- 已明确本次要走“重开 Mission”而非继续复用旧 runner 状态。

**输出物**
- 统一术语表：`annotationId`、`annotationKey`、`taskId`、`formId`、`workflowNode`、`reviewRound`；
- 两仓字段映射表与兼容窗口清单；
- feature flag / rollback 规则；
- 新 mission 的验证范围基线。

**验证重点**
- 术语不冲突；
- 每个 milestone 的责任边界无重叠；
- 验证合同能映射到后续 worker 任务。

## M2：ReviewSnapshot 恢复统一

**入口条件**
- M1 完成并冻结权威字段语义；
- 已盘点 `task records`、`workflow/sync`、`import package` 三类恢复入口。

**输出物**
- 统一 `ReviewSnapshot` 语义层；
- task restore / workflow sync restore / import restore 共用的 adapter 路径；
- stale state clearing 与 dedupe 规则。

**验证重点**
- 同一任务从不同入口恢复结果一致；
- 从有记录任务切换到空任务能清除旧场景；
- 首次空任务进入的 `skipClearOnEmpty` 行为保持可控。

## M3：评论真源解耦

**入口条件**
- M2 已确保 detached comments 能在 restore 时重新挂回对应批注；
- reviewer / designer 两侧线程 UI 已梳理出当前依赖点。

**输出物**
- 独立 comment source / thread store；
- timeline 读写从 annotation inline comments 解耦；
- reviewer / designer 线程语义统一。

**验证重点**
- 评论的创建、回复、编辑、删除不依赖 annotation 内联字段；
- 当前轮次与累计历史可正确区分；
- 评论加载失败、空态、权限态清晰可见。

## M4：后端元数据扩展

**入口条件**
- M1 已定义字段；
- M2/M3 已明确前端需要的稳定元数据。

**输出物**
- records / comments / workflow sync 的 metadata 扩展；
- `annotationKey`、`workflowNode`、`reviewRound` 等字段进入兼容窗口；
- API 读写与聚合结构保持旧字段可消费。

**验证重点**
- curl/真实接口验证字段透传；
- workflow node 归属与 task context 不漂移；
- metadata 扩展前后，前端恢复结果一致。

## M5：实时协同收敛

**入口条件**
- 后端接口已具备稳定 comment / record / task status 事件语义；
- 前端已有统一 refresh 入口可接入 websocket。

**输出物**
- user-scoped websocket 事件使用规则；
- comment / record / task status 的 targeted refresh；
- heartbeat、重连、HTTP fallback 的一致性策略。

**验证重点**
- comment_added 不重复插入、不乱序；
- reconnect 后线程与确认记录收敛；
- 无 websocket 时仍可通过 HTTP 正常工作。

## M6：task 级草稿隔离与连续性

**入口条件**
- M2 已实现 confirmed replay 与 task context 恢复；
- M3/M5 已让线程与协同不依赖共享草稿态。

**输出物**
- `project + db + taskId` 级别的草稿作用域；
- reviewer 直接发起批注/测量与确认入口的 task 绑定；
- designer returned-task continuity 与 resubmit 连续性。

**验证重点**
- 切换任务不会串草稿；
- 返回/重提仍绑定同一 `taskId`；
- 当前轮与历史累计在 UI 上可区分。

## M7：draft / confirmed 双层渲染

**入口条件**
- M6 已保证草稿隔离；
- M2 已让 confirmed evidence 可独立 replay。

**输出物**
- draft layer 与 confirmed layer 明确分层；
- confirm 只消耗 draft，不覆盖 confirmed；
- reopen / import / export / resubmit 下的层级不混淆。

**验证重点**
- 已确认记录区始终可见且信息完整；
- confirm 前后场景差异可解释；
- 双层切换具备回退开关。

## 5. 风险与回滚策略

### 5.1 主要风险

- **跨仓契约推进不一致**：前端先行、后端字段未到位会导致半兼容状态；
- **恢复统一阶段回归风险高**：task / workflow / import 三入口稍有差异就会造成场景不一致；
- **双层渲染改动大**：viewer 与 tool store 若同时重构，容易引发大面积回归；
- **mission 重开后范围失控**：如果不严格按 milestone 拆 worker，容易再次形成难启动的大包任务。

### 5.2 回滚策略

- 每个 milestone 都保留旧链路兼容读取能力；
- 使用 feature flag 控制 SHADOW、DUAL_READ、CUTOVER；
- 先做 adapter / snapshot / thread source，再做 viewer 双层，不一次性推翻；
- 若新 Mission 过程中再次卡住，至少保留“当前里程碑输入 + 输出 + 验证结果”作为下一次重开的最小包。

## 6. 重开 Mission 检查清单

- [ ] 新 Mission 明确引用本计划与 Mission 说明两份文档；
- [ ] 将原 mission 中可复用的 milestone / feature / validation 结论转为新的输入，而不是直接沿用旧 runner 状态；
- [ ] 明确前端仓、后端仓路径与验证环境；
- [ ] 将 worker 拆分到 milestone 级或 feature 级，避免一次性超大任务；
- [ ] 每个 worker 都绑定输入文档、预期输出、验证方式与回退规则；
- [ ] 下一次 Mission 启动前先确认 artifacts 完整、工作目录正确、无旧运行态残留；
- [ ] 验证计划至少覆盖 `lint`、`type-check`、`vitest`、必要浏览器验证/接口验证。

## 7. 建议的重开顺序

1. 先用新 Mission 说明创建新的 planning package；
2. 首批只放 M1 + M2 的 worker，确认 runner 能正常起跑；
3. 之后再逐步加入 M3、M4、M5；
4. M6、M7 作为后半程执行，避免一开始就把高风险 viewer 改造打包进去。

---

这份“重开 Mission”计划的核心不是重写已有方案，而是把现有成果压缩成一套更容易重新启动、拆分执行、逐步验证的输入包。
