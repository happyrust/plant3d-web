## 1. 摘要（TL;DR）

`ReviewPanel.vue`（jh / sh 校核工作台）在 **ccb8d08（2026-04-23）** 通过 PR 8 接入「卡片列表 ⇄ 批注表格」tab 切换；在 **a644ba3（2026-05-06）** 时该功能仍完整在主线。其后一次将 **028de56（2026-04-25，批注体系 M2-M6 重构）** 反向合入主线时，PR 8 在 ReviewPanel.vue 中的所有改动被整段覆盖；合并 commit **6ad374b** 又采用了「无 AT」一侧。结果：

- ReviewPanel.vue 不再包含 `AnnotationTableView` 任何引用；
- 但 ribbon 按钮 / DockLayout 分发 / bus / 测试用例 / onboarding 引导 **全部完整保留**；
- 用户视角：点 ribbon「批注表格」按钮无反应，审核员只能看卡片列表；
- 6+ 条 PR 8/PR 9 vitest 用例必死，但因 AGENTS.md 约定「默认不跑 vitest」未被发现。

决策：采用 **Adapter 增量回填方案**，最小侵入恢复 PR 8 功能；同步加入测试守护规则，防止再次因 rebase / cherry-pick 整段消失。

## 3. 根因分析

### 3.1 直接根因
028de56（2026-04-25，作者 happyrust）的 ReviewPanel.vue 实际对应 **ccb8d08 之前的状态**——即该 commit 把 PR 8 当作不存在地完成了 M2-M6 重构。当这个 commit 之后被反向 cherry-pick / rebase 入主线时，PR 8 在 ReviewPanel.vue 的所有改动被整段覆盖。`git log -G 'AnnotationTableView' -- src/components/review/ReviewPanel.vue` 中**没有 `-AnnotationTableView` 行**，说明丢失发生在「整树覆盖」而非「显式删除」中，这是 rebase / 反向合并的典型痕迹。

### 3.2 根本根因
1. **缺乏测试 enforcement：** AGENTS.md 明文「默认不跑 vitest」，导致 PR 8/9 共 6+ 条用例长期必死无人察觉。
2. **缺乏跨 commit 一致性守护：** ReviewPanel.vue 当前已经 1993 行，混合了 workflow / embed / annotation / measurement / debug 多职责，本地分支合并时人工 diff 难以发现整段消失。
3. **双胞胎组件维护成本：** `DesignerCommentHandlingPanel` 和 `ReviewPanel` 都各自实现「split / table tab + bus 订阅 + 持久化」，相同模式在两处独立维护，DCH 没丢但 ReviewPanel 丢了，单测互不连坐。
4. **MVP 验收依赖人工：** 2026-04-23 的 `annotation-table-mvp-verification.md` 是一次性手测报告，没有沉淀为自动回归。

## 4. 决策

### 4.1 修复策略

采用 **方案 A · Adapter 增量回填**（详见 `docs/plans/2026-05-17-reviewer-annotation-table-restore-plan.md` §2）。

理由：
- 最小侵入：当前 ReviewPanel.vue 的 `allAnnotationItems` 用本地 `AnnotationListItem` 类型，而 `AnnotationTableView` 接受 `AnnotationWorkspaceItem[]`，加 30 行适配器纯函数即可解决类型鸿沟。
- 不冒大重构险：reviewer 工作台的 confirm / submit / embed / passive workflow 等逻辑都依赖现有 list 结构，重构成本和回归面积过大。
- 可独立 commit / 独立 revert：6 个 commit 各自承担单一职责（adapter / script / template / test / smoke / docs）。

### 4.2 不选 B 重构方案的理由
方案 B 是把 ReviewPanel 也对齐 `AnnotationWorkspace + AnnotationTableView` 双视图（与 a644ba3 / DCH 形态一致），但会触及 embed / passive workflow / confirm 流程的多处假设，单 PR 风险过高，留给后续 PR 推进。

### 4.3 不选 C 仅恢复 ribbon 路由的理由
痛点本质是「表格视图本身不在」，仅修按钮路由不能解。

## 11. 2026-05-18 补丁：批注表格视图 form_id scope 修复

### 11.1 现象

2026-05-17 的 v-if 修复让审核面板的批注列表/表格切换变得 status-agnostic
（任何 task 状态进去都能切换 + 看到表格 empty state），但 `annotationWorkspaceItems`
computed 没有 form_id 过滤。在 SJ 经 PMS 外部流程打开**被驳回单据**这条主链路
（参见 `.plannotator/plan-sj-reject-ui.md`）上，切到「批注表格」会把其它 form_id
的批注一并显示，违反 plan-sj-reject-ui.md §6「UI 不显示跨单据批注」约定。

### 11.2 根因

`src/components/review/ReviewPanel.vue` 当前 HEAD：

- 第 1355–1424 行 `allAnnotationItems`（喂给卡片列表 split 视图）按
  `isExternalSjFormFocused` 走手写过滤
- 第 1429–1442 行 `annotationWorkspaceItems`（喂给批注表格 table 视图）**完全不过滤**

两条数据源 scope 策略不一致：同一个面板的卡片列表会按 form_id 收敛，
表格却泄露全集，用户切到表格视图会感受到「批注变多了 / 出现不属于本单据的批注」。

对比 `DesignerCommentHandlingPanel.vue` 第 518–535 行：已统一用
`scopeAnnotationWorkspaceItemsByFormId(items, currentFormId || ...)` 在一个调用里
做 form_id 过滤；ReviewPanel 与 DCH 之间也存在双轨。

### 11.3 修复

按 `docs/plans/2026-05-18-reviewer-annotation-table-formid-scope-plan.md`
方案 A1（最小侵入）：

- 在 `ReviewPanel.vue` import 区追加 `scopeAnnotationWorkspaceItemsByFormId`
- 把 `annotationWorkspaceItems` computed 改为先 `buildAnnotationWorkspaceItems`
  构造全集，再在 `isExternalSjFormFocused.value === true` 时按
  `activeReviewFormId.value` 过滤；其它模式放行全集

行为对齐：与 `allAnnotationItems` 严格一致；不动审核员 (jh/sh/pz) 默认行为。

### 11.4 防御

  「SJ 外部 form_id 聚焦」「manual workflow 不收敛」「passive workflow + jd 角色不收敛」

## 12. 2026-05-18 数据源统一：split / table 双轨终结

## 13. 2026-05-18 SJ 入口全面收敛到 ReviewPanel
